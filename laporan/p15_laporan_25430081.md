1. Tujuan Praktikum

- Menjelaskan dan mengimplementasikan kerangka kerja kualitas data (Data Quality Framework/TDQM) yang mencakup dimensi kelengkapan (`completeness`), validitas (`validity`), keunikan (`uniqueness`), dan konsistensi (`consistency`).
- Menulis dan mengeksekusi kueri pemindaian data (`data profiling`) di MariaDB/MySQL Shell untuk menemukan dan mengelompokkan anomali data sebelum diproses.
- Menggunakan tabel penampung sementara (`staging table`) dengan tipe data teks longgar (`VARCHAR`) untuk menerima impor data kotor tanpa terhenti oleh galat skema.
- Menerapkan fungsi pembersihan berbasis ekspresi reguler (`REGEXP_REPLACE`), fungsi manipulasi teks (`UPPER`, `LOWER`, `TRIM`, `CONCAT`), serta konversi tanggal aman (`STR_TO_DATE` dan `LAST_DAY`).
- Mengimplementasikan penyaringan duplikasi menggunakan fungsi jendela `ROW_NUMBER() OVER (...)` serta menyusun laporan audit kualitas data secara profesional.

2. Ringkasan Dasar Teori
Pada tahap pengelolaan kualitas data (Milestone Proyek Modul 15), beberapa konsep utama yang diterapkan meliputi:
- Kerangka Kerja Kualitas Data (TDQM): Proses terstruktur untuk menjamin bahwa data layak digunakan (`fit for use`). Meliputi dimensi `Kelengkapan` (tidak ada atribut penting yang NULL/kosong), `Validitas` (data sesuai aturan format seperti digit NPM atau format nomor telepon), `Keunikan` (tidak ada rekaman ganda untuk entitas yang sama), dan `Konsistensi` (penulisan variabel seragam).
- Strategi Staging vs Direct Load: Memuat data mentah (`raw data`) langsung ke tabel produksi utama berisiko memicu kesalahan sistem (`strict mode error`) atau merusak integritas data. Oleh karena itu, data diimpor terlebih dahulu ke `tabel penampung (`staging table`)` berstruktur longgar (`mahasiswa_impor`) agar seluruh baris dapat ditampung dan diurai secara aman.
- Ekspresi Reguler (`REGEXP` & `REGEXP_REPLACE`): Fitur SQL untuk mengenali dan membersihkan pola karakter. Digunakan untuk menghapus karakter non-numerik pada NPM/nomor HP (`REGEXP_REPLACE(no_hp, '[^0-9]', '')`), menyelaraskan format nomor telepon berawalan `+62` menjadi `08`, serta mengecek keabsahan pola teks.
- Validasi Tanggal dan Kondisional (`CASE WHEN`): Pembersihan nilai non-standar atau tanggal tidak valid (misalnya tanggal 31 September) ditangani menggunakan kondisional `CASE WHEN` dipadukan dengan `STR_TO_DATE` dan `LAST_DAY`, sehingga data yang tidak masuk akal otomatis dikonversi menjadi `NULL` atau ditolak tanpa menghentikan eksekusi kueri.
- Pembasmian Duplikasi (`Deduplication`): Penggunaan fungsi analisis `ROW_NUMBER() OVER (PARTITION BY npm_mhs ORDER BY baris)` untuk memberi nomor urut pada rekaman dengan NPM yang sama, sehingga hanya baris pertama (`urut = 1`) yang diizinkan dipindahkan ke tabel utama.

4. Jawaban Titik Analisis

- Titik Analisis 1: Mengapa impor data mentah dari pihak luar/sistem lama tidak boleh dipaksakan langsung ke tabel utama (`production table`) dengan batasan (`constraint`) ketat?
  Jawab: Memaksakan impor langsung ke tabel utama akan menyebabkan proses impor gagal total (`abort/crash`) saat menemukan satu saja baris data yang melanggar constraint (misalnya `duplicate primary key`, `foreign key error`, atau `format mismatch`). Pendekatan tabel staging (`VARCHAR` longgar) memungkinkan seluruh data mentah masuk terlebih dahulu sehingga analisis profil data (`profiling`) dan pembersihan (`cleansing`) dapat dilakukan secara menyeluruh tanpa mengganggu integritas basis data produksi.

- Titik Analisis 2: Mengapa validasi nomor HP lebih baik menggunakan kombinasi `REGEXP_REPLACE` dan `CASE WHEN` dibandingkan dengan sekadar menyaring `WHERE length(no_hp) = 12`?
  Jawab: Panjang karakter bukan jaminan format nomor valid. Nomor HP mentah sering kali mengandung variasi format seperti pemisah strip (`0812-3456-7890`), awalan negara (`+628123456789`), atau spasi. Menggunakan `REGEXP_REPLACE(no_hp, '[^0-9]', '')` terlebih dahulu akan membersihkan seluruh karakter non-angka, lalu `CASE WHEN` akan menstandarkan awalan `62` atau `8` menjadi `08`. Jika hanya mengukur `LENGTH()`, data valid yang menggunakan pemisah atau kode negara akan salah terbuang.

- Titik Analisis 3: Bagaimana fungsi jendela `ROW_NUMBER()` bekerja dalam menyaring duplikasi data pendaftaran di tabel staging?
  Jawab: Fungsi `ROW_NUMBER() OVER (PARTITION BY npm_mhs ORDER BY baris)` mengelompokkan data berdasarkan atribut kunci unik (`npm_mhs`) dan memberi nomor urut otomatis (1, 2, 3...) berdasarkan waktu atau urutan masuknya data (`baris`). Ketika dilakukan filter `WHERE urut = 1` pada kueri `INSERT`, sistem hanya mengambil rekaman pertama yang sah dan mengabaikan seluruh rekaman duplikat berikutnya secara atomik.

Kendala yang sempat dihadapi pada saat eksekusi praktikum di antaranya:
- ERROR 2 (File Not Found) pada perintah SOURCE: Terjadi akibat ketidaksesuaian jalur direktori (`path`) saat menjalankan `SOURCE` di XAMPP Shell. Diatasi dengan mengarahkan `path` langsung ke lokasi riil berkas pada drive, yaitu `SOURCE D:/basis_data_25430081/p15_kualitas_25430081.sql;`.
