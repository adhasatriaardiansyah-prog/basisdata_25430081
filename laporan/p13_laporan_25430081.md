1. Tujuan Praktikum

2. Ringkasan Dasar Teori
Pada tahap pengembangan sistem informasi per peran (Milestone Proyek Modul 13), beberapa konsep utama yang diterapkan meliputi:
- View (Tabel Virtual): Objek basis data yang menyimpan kueri `SELECT` dan menyajikannya dalam bentuk tabel logis. View tidak menyimpan data fisik secara langsung melainkan mengambilnya dari tabel dasar (base table) secara real-time.
- Minimalisasi Akses & UU PDP: Prinsip keamanan di mana pengguna hanya diberikan akses terhadap kolom data yang benar-benar dibutuhkan. Informasi sensitif seperti `no_hp_mahasiswa` atau `email_pribadi_mahasiswa` disembunyikan dari jendela View yang diakses oleh pihak luar/umum.
- Hak Akses Berbasis Peran (RBAC & Role): Pengelompokan izin akses menggunakan `CREATE ROLE` yang kemudian ditetapkan ke akun pengguna (`GRANT r_dosen_081 TO 'dosen_081'`). Hak akses diberikan secara spesifik ke View (`GRANT SELECT ON akad_081.v_dosen_mahasiswa`) dan BUKAN ke tabel dasar.
- Impersonasi DEFINER vs INVOKER: Keamanan eksekusi View di MariaDB di mana mode `DEFINER` mengeksekusi View dengan hak akses pembuatnya, sedangkan `INVOKER` mengeksekusi View dengan hak akses pengguna yang sedang aktif memanggilnya.
- Integritas Data `WITH CHECK OPTION`: Fitur keamanan pada View yang memvalidasi setiap operasi `INSERT` atau `UPDATE` agar tetap sesuai dengan klausa `WHERE` pada definisi View tersebut.

4. Jawaban Titik Analisis

- Titik Analisis 1: Apa yang terjadi jika akun pembuat View (DEFINER) dihapus dari MariaDB, dan bagaimana solusinya?
  Jawab: Jika akun pembuat View (`mhs_081` / DEFINER) dihapus dari server, maka saat pengguna lain mencoba memanggil View tersebut akan muncul `ERROR 1449 (The user specified as a definer does not exist)`. Solusinya adalah mengubah DEFINER menggunakan klausa `ALTER DEFINER = 'root'@'localhost' VIEW ...` atau membuat kembali akun DEFINER yang hilang tersebut.

- Titik Analisis 2: Mengapa sistem menolak perintah akses langsung ke tabel dasar (ERROR 1142) namun mengizinkan akses ke View (ERROR 1054 vs Berhasil)?
  Jawab: Sistem menolak akses ke tabel dasar (`ERROR 1142: SELECT command denied`) karena hak akses `GRANT SELECT` hanya diberikan ke objek View dan tidak diberikan pada tabel `mahasiswa`. Sedangkan ketika mengakses kolom sensitif via View muncul `ERROR 1054: Unknown column` karena kolom tersebut memang sengaja dieksklusi (disembunyikan) dari proyeksi klausa `SELECT` saat View diciptakan.

- Titik Analisis 3: Bagaimana cara kerja klausa WITH CHECK OPTION dan apa akibatnya jika pengguna mencoba memperbarui data yang melanggar kondisi WHERE pada View?
  Jawab: `WITH CHECK OPTION` berfungsi mencegah pembaruan data yang membuat data tersebut "menghilang" dari View. Jika pengguna mencoba mengubah status mahasiswa pada `v_mahasiswa_bermasalah` menjadi `'Aktif'`, MariaDB akan menolak operasi tersebut secara mutlak dengan pesan `ERROR 1369 (CHECK OPTION failed)`.

7. Pembahasan dan Kendala
Kendala yang sempat dihadapi pada saat eksekusi awal di antaranya:
- ERROR 1054 (Unknown column 'dk.id_mhs'): Terjadi karena relasi tabel `detail_krs` tidak terhubung langsung ke `mahasiswa`. Diperbaiki dengan melengkapi urutan JOIN melalui tabel `krs` (`m.id_mhs = k.id_mhs` DAN `k.id_krs = dk.id_krs`).
- ERROR 1054 (Unknown column 'dk.id_mk'): Diperbaiki dengan menambahkan tabel perantara `kelas` (`dk.id_kelas = k_ls.id_kelas` DAN `k_ls.id_mk = mk.id_mk`).
- ERROR 1146 (Table 'v_rekap_ipk_prodi' doesn't exist): Terjadi akibat ketidaksesuaian nama View pada skrip `GRANT` role. Diperbaiki dengan mengarahkan izin akses ke View `v_rekap_prodi`.
- ERROR 1045 (Access denied for user 'dosen_081'): Diatasi dengan melakukan `ALTER USER 'dosen_081'@'localhost' IDENTIFIED BY '12345';` pada sesi `root` untuk menyelaraskan kata sandi pengujian.
